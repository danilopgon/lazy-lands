## Scope (two coupled parts)

Defined by `docs/10-roadmap.md` → "### Per-section regeneration (MVP — deferred from Block 8, before Block 9)".

1. **Contract alignment (prerequisite).** Align the generated-session contract with the SEVEN
   editable handoff sections before adding regeneration: `synopsis`, `goal`, `opening`, `beats`,
   `encounters`, `factions`, `arcs`. The same canonical section IDs and provenance rules MUST flow
   through the LLM prompt, the Pydantic output contract, `generated_content` persistence, the
   session-detail API, localized frontend labels, and the editable draft UI. Keep READ
   compatibility for existing Block 8 drafts.
2. **Per-section regeneration.** DM regenerates an INDIVIDUAL section with a fresh LLM call that
   preserves the rest of the draft. Requires `POST /sessions/{id}/regenerate-section` and
   per-section prompt templates. Replaces the disabled "Coming later" affordance. Must ship before
   Block 9 (PDF export).

## Current State

**Backend** (`services/api/app/modules/generation/`): `application/contracts.py` defines
`GeneratedSessionOutput` with flat fields `title, synopsis, main_objective, twist,
encounters: list[Encounter], faction_reactions: list[FactionReaction],
arc_progression: list[ArcProgression], continuity_links, generated_content: GeneratedDraftContent | None`.
`content_for_persistence()` persists only 3 sections (`synopsis`, `main_objective`, `twist`) —
`encounters`/`faction_reactions`/`arc_progression` are dropped, confirming the PR #51 gap.
`generate_session_v1.jinja` (lines 65-72) only instructs the LLM to emit those same 3 sections.
`generate_session.py` (`GenerateNextSessionUseCase`) persists `content_for_persistence()` verbatim;
`PROMPT_VERSION = "generate_session_v1"` and `trace_json` conventions live here. `api/routes.py` has
only `POST /campaigns/{campaign_id}/generate-session` — no `regenerate-section` route exists.

**Sessions module**: `application/read_models/session_detail.py` exposes
`generated_content: dict[str, Any] | None` (opaque, unvalidated on read). `session.py` list read
model exposes `has_generated_content: bool` (derived in `infrastructure/repository.py:164-188`,
stripping the JSON blob). `api/routes.py` has `GET /sessions/{id}` and `PATCH /sessions/{id}`
(full-object `generated_content` replace, no server-side diffing —
`application/commands/update_session.py`). No explicit ownership checks in code — RLS is enforced
entirely by the per-user Supabase client injected via DI; a new endpoint should follow the same
pattern.

**Frontend** (`apps/web/`): `lib/sessions/schemas.ts` has `generatedSectionSchema`
(`id, label, body, origin`) plus a stale `generateSessionResponseSchema` still mirroring the old
flat 6-field shape. `lib/sessions/section-label.ts` allowlists the OLD 6 ids (`synopsis`,
`main_objective`, `twist`, `encounters`, `faction_reactions`, `arc_progression`) — none match the
7-section handoff target. `components/sessions/generated-session-view.tsx` renders sections
generically, has working inline edit+PATCH, and a disabled "Regenerate" button with no
`onClick`/endpoint wiring (`{t('regenerateComingLater')}`).

**Handoff visual contract**: `route-map.md` points `/campaigns/:id/sessions/:sid` to
`views-sessions.jsx`, but the real `GeneratedSession` component lives in
`handoff/app/views-prepare.jsx` (stale map entry — known, low-priority, tracked in engram
`backlog-deferred-mvp-items`). `views-prepare.jsx`'s `GeneratedSession` renders each section with
`OriginBadge`, `Edit`, and `Regenerate` links; regenerating shows a per-section spinner ("The Scribe
is rewriting") and a toast ("Section regenerated by the Scribe"). Legend text confirms regeneration
**replaces** an edited section's body and resets `origin` back to `"scribe"`. `handoff/app/data.js`
(lines 198-207) gives the authoritative 7 canonical ids/labels: `synopsis` (Synopsis), `goal`
(Session goal), `opening` (Opening scene), `beats` (Main beats), `encounters` (Encounters, bullet
text), `factions` (Faction reactions, bullet text), `arcs` (Arc progression, bullet text).

**PDF export confirmation**: `handoff/app/views-export.jsx` renders the exported document entirely
from `sections[].label`/`.body` (bullet lines detected by a leading `•`) — no structured
`Encounter`/`FactionReaction`/`ArcProgression` data is consumed anywhere in export. This confirms
flat text sections are sufficient for Block 9 and removes the "keep structured fields for PDF"
argument.

## Approaches

1. **Sections-only contract (drop flat structured fields)** — `GeneratedSessionOutput` becomes
   `{title, sections: list[7 required ids]}`; `Encounter`/`FactionReaction`/`ArcProgression`/
   `main_objective`/`twist` retired.
   - Pros: matches handoff and confirmed PDF-export needs exactly; single representation; simplest
     regeneration semantics (regenerate = new body for section X).
   - Cons: breaking change to `GenerateSessionResponse`/`generateSessionResponseSchema`; requires an
     explicit read-compat shim for legacy 3-section rows.
   - Effort: Medium-High.
2. **Keep structured fields, derive 7 text sections server-side** — add a `to_sections()` helper.
   - Pros: preserves structured data "just in case."
   - Cons: two parallel representations to keep in sync; per-section regeneration would desync
     structured data from text; PDF-export finding shows this data has no consumer. Not recommended.
   - Effort: Medium.
3. **Per-section prompt strategy** — one prompt template per section id (recommended) vs a single
   parametrized template. Per-template is chosen for consistency with the existing
   one-purpose-per-template convention, sharing a Jinja include/macro for the duplicated
   context-rendering block.
4. **`regenerate-section` endpoint shape** — returns the full `SessionDetailResponse` (recommended),
   matching the existing `update_session.py` "PATCH returns whole session" pattern, over returning a
   single section and requiring frontend-side merge logic.

## Recommendation

Adopt Approach 1 (sections-only contract) plus per-section prompt templates and a
full-session-returning `regenerate-section` endpoint. Two decisions remain for `sdd-propose`:
(a) exact read-compat strategy for legacy 3-id rows (`main_objective`/`twist`) once the derivation
fallback is retired from new writes, and (b) disposition of `twist` specifically (drop / fold into
`beats` or `opening` / keep as a non-handoff 8th section).

## Risks

- Renaming `main_objective`→`goal` and dropping `twist` is breaking for existing Block 8 generated
  rows in any deployed environment — needs explicit read-compat design before removing
  `content_for_persistence()`'s legacy branch.
- `docs/06-api-contracts.md` has no documentation at all for `GET/PATCH /sessions/{id}` today — this
  change should add it alongside the new endpoint, not just the new endpoint.
- No existing use case resolves `campaign_id` from `session_id` for regeneration context-building —
  small but real new plumbing.
- The frontend regenerate control is fully unwired (not a toggle) — expect a non-trivial
  `generated-session-view.tsx` diff, not a small patch.
- `route-map.md` stale entry could mislead a fresh design/apply agent if not called out explicitly
  in the design doc.
