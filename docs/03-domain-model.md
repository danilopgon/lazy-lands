# Domain Model

This document defines the main domain concepts of Lazy Lands.

## Core entities

### User

Represents an authenticated Supabase user.

The application does not manage passwords directly. Authentication is delegated to Supabase Auth.

Main fields:

- `id`
- `email`
- `created_at`

### Campaign

Represents a long-running tabletop RPG campaign.

Main fields:

- `id`
- `user_id`
- `title`
- `description`
- `world_state`
- `accumulated_summary`
- `summarized_up_to_session`
- `created_at`
- `updated_at`

Rules:

- A campaign belongs to one user.
- A campaign has many NPCs.
- A campaign has many factions.
- A campaign has many sessions.
- A campaign has many arcs.
- A campaign has many memory facts.

### NPC

Represents a non-player character.

Main fields:

- `id`
- `campaign_id`
- `name`
- `description`
- `current_state`
- `motivation`
- `content_source`
- `created_at`
- `updated_at`

Rules:

- NPCs are scoped to a campaign.
- NPCs can be generated by AI or manually edited by the DM.
- Edited NPC fields should be considered authoritative.

### Faction

Represents a relevant organization or group in the campaign.

Main fields:

- `id`
- `campaign_id`
- `name`
- `description`
- `current_stance`
- `goals`
- `content_source`
- `created_at`
- `updated_at`

Rules:

- Factions are scoped to a campaign.
- Faction reactions should be considered during next-session generation.

### Arc

Represents an open narrative thread, conflict, promise or unresolved situation.

Main fields:

- `id`
- `campaign_id`
- `title`
- `description`
- `status`
- `priority`
- `created_at`
- `updated_at`

Possible status values:

- `open`
- `resolved`
- `dropped`

Rules:

- Only open arcs are included in generation context.
- Resolved and dropped arcs remain stored but are excluded from active context.

### Session

Represents a played or generated campaign session.

Main fields:

- `id`
- `campaign_id`
- `session_number`
- `summary`
- `consequences`
- `generated_content`
- `trace_json`
- `created_at`
- `updated_at`

Rules:

- Sessions are ordered by `session_number`.
- A played session can update the accumulated summary.
- A generated session may contain trace metadata about the generation process.

### MemorySuggestion

Temporary AI-generated candidate memory.

This is not canon.

Main fields:

- `content`
- `type`
- `importance`
- `reason`
- `source_session_id`

Rules:

- Memory suggestions are not persisted as active memory unless accepted by the DM.
- The DM can accept, reject or edit them.

### MemoryFact

A memory accepted by the DM as active campaign context.

Main fields:

- `id`
- `campaign_id`
- `source_session_id`
- `content`
- `type`
- `importance`
- `status`
- `created_at`
- `updated_at`

Possible status values:

- `active`
- `archived`

Rules:

- Only active MemoryFacts are included in generation context.
- MemoryFacts are part of campaign continuity.
- MemoryFacts should be human-approved.

### GeneratedSessionOutput

Structured AI output for a next-session proposal. Sections-only contract — there is
no flat/derived shape. `Encounter`, `FactionReaction`, and `ArcProgression` as
standalone models are retired, along with the top-level `main_objective` and
`twist` fields; a twist is woven into the `beats`/`opening` section bodies
instead of being a separate field.

Main fields:

- `title`
- `sections` — exactly the 7 canonical `GeneratedDraftSection` entries below, in
  order
- `continuity_links`

Rules:

- The backend must validate this output before showing or persisting it
  (`extra="forbid"`; `sections` must be exactly the 7 canonical ids in order).
- Invalid output must be rejected; nothing is persisted.
- The DM must treat generated content as a draft.

### GeneratedSection / GeneratedDraftSection

One editable generated-content section with provenance. Persisted on
`sessions.generated_content.sections[]`. The 7 canonical section ids, fixed
order:

1. `synopsis` — Synopsis
2. `goal` — Session goal
3. `opening` — Opening scene
4. `beats` — Main beats
5. `encounters` — Encounters
6. `factions` — Faction reactions
7. `arcs` — Arc progression

Fields:

- `id`
- `label`
- `body`
- `origin` — `scribe` (untouched Scribe proposal) or `edited` (DM has edited it)

Rules:

- `GeneratedDraftSection.origin` is always `scribe` (brand-new LLM output).
- Regenerating a section resets its `origin` to `scribe`, even if it had
  previously been `edited` — a fresh Scribe proposal always overwrites DM edits
  on that one section (and only that one).

### RegeneratedSectionOutput

Structured AI output for `POST /sessions/{id}/regenerate-section`. Carries only
the rewritten `body` — the id, label, and origin are supplied by the backend, not
the LLM.

Rules:

- The backend must validate this output before persisting it (`extra="forbid"`).
- On validation failure, the previous section body/origin is left untouched and
  nothing is persisted.

## Value objects

### ContentSource

Represents where a field came from.

Possible values:

- `llm`
- `edited`
- `manual`

Rules:

- AI-generated content can be edited by the DM.
- Edited content is more authoritative than generated content.

### Importance

Used for memories and arcs.

Possible values:

- `low`
- `medium`
- `high`

## Domain invariants

- A user must not access another user's campaign data.
- AI output must not be trusted until validated.
- AI suggestions do not become canon automatically.
- The DM is the authority over campaign memory.
- Generation context must include only data belonging to the active campaign.
